# kahviraspi go-live — 2026-09-16 ~16:00

## What is actually wrong

The reader service is **running but wedged**, not dead. Evidence from the 14:11 snapshot:

| fact | source |
|---|---|
| `kahvi-reader` last started **Sep 15 17:12:33** (PID 8628) and has logged **nothing** in the 21 h since | `system.journal.log`, every `reader service up` line |
| the bot's failure is `socket.timeout` on `recv`, not connection-refused — so something **is** listening and just never replies | `kahvibot.journal.log` line 250 traceback |
| ~every bot photo today fell back to fswebcam (13:23, 13:31, 13:44, 14:04, 14:07 …) | `kahvibot.journal.log` |
| `readings-2026-09.jsonl` has **22 lines** in the old fat schema, written by the *bot's* fallback — not the reader's slim `a/t_c/fm` records at 10 s | `readings-2026-09.jsonl` |

`kahvisampler` being dead is **not** a fault — `install_reader.sh` retires it, and
PIPELINE.md §3 records the reader live since 2026-09-15. Do not re-enable it.

**Prime suspect: the USB camera wedged and took the reader's loop with it.**

`camera.py` guards the capture with `subprocess.run(cmd, timeout=8.0)`. That guard is incomplete:
on timeout Python sends SIGKILL to fswebcam and then **waits for it to reap**. A process blocked in
uninterruptible `D` state on a stuck USB device does not die on SIGKILL — it dies when the driver
returns, which may be never. With **327 `uvcvideo: Failed to resubmit video URB (-1)`** errors and
under-voltage climbing to 260/day, that is the likely state. It matches every symptom: no log line
(the tick never completes), no readings, the process alive, and `capture()`'s `finally` never
reached so the camera flock stays held.

Ruled out: the camera lock itself. `run_daemon.py:81` builds `FswebcamCamera` without `lock_wait`,
so it defaults to `LOCK_NB` and raises `CaptureBusy` rather than blocking. The 0666 tmpfiles lock is
still worth installing (the hand-deploy skipped it, and it prevents a *different* failure where the
konsta-run reader cannot open a root-created lock file), but it is not the wedge.

Still unconfirmed until `00_diagnose.sh` runs: the hand-deploy also skipped the `sed` that rewrites
the unit's paths, so the installed unit may still carry the template's `/home/marci/...` paths.

`00_diagnose.sh` distinguishes these directly: a thread in `D` state with a `usb`/`uvc` `wchan`, or a
leftover fswebcam process, is the camera hang; `VERIFY` failing again right after a restart points at
the unit paths instead.

## Sequence at ~16:00

You must be **back on the guild WiFi** (`Fyysikkokilta`, 192.168.50.x). The Pi is LAN-only —
SSH from your current location times out, which is why none of this ran at 14:11.

```bash
cd deploy_2026-09-16
bash 00_diagnose.sh                 # 1. READ-ONLY, ~30 s. Changes nothing.
MODE=repair bash 10_deploy.sh       # 2. the fix + verification, ~2 min
```

`00_diagnose.sh` answers the one open question by printing `systemctl cat kahvi-reader`
(which unit is really installed) plus per-thread `wchan` for the wedged PID — that names the
blocking syscall, so you will know if it is the camera lock or something else before you touch it.

**Read step 1's output before running step 2.** If the per-thread `wchan` shows the reader parked on
a lock or `/dev/video0`, `MODE=repair` is the right call: it installs the 0666 tmpfiles lock and
restarts the daemon. If the installed unit turns out to have wrong paths or you want the new
pipeline anyway, use `MODE=pipeline` (see below).

### Verification is built in
`10_deploy.sh` will not tell you it worked because the restart returned 0. It checks: the
`reader service up` line appears; the IPC socket **answers an `alive` ping**; the readings file
**grows within 45 s**; the bot stops logging `reader service unavailable`; and it prints
`vcgencmd get_throttled`. It ends in `VERIFY: PASS` or `VERIFY: FAIL`.

### If it fails
```bash
STAMP=<printed by 10_deploy.sh> bash 90_rollback.sh           # restore units
STAMP=<...> FULL=1 bash 90_rollback.sh                        # + stop reader -> bot on fswebcam
```
`FULL=1` is today's status quo: slow photos, working bot. A fine place to stop if the room needs
coffee more than it needs 3 s latency.

## MODE=pipeline — the bigger change, only if you mean it

Ships the local `reader-pipeline` branch (`8ccfadb`, **not pushed to any remote**, so it goes over
as a tar) and runs `install_reader.sh` properly. That is not a repair, it is a different reader:

- runs from the kahvibot checkout, not `/home/konsta/coffee-reader`
- `--filter` — the RBPF volume/temperature particle filter — plus MQTT plug power, so it needs mosquitto auth
- readings move to `/home/konsta/coffee-data/`, **new slim schema**; the bot's `coffee_reader_log`
  must be repointed by hand and kahvibot restarted, or `/graph` reads the wrong file
- `MemoryMax` 260M → 320M on a 909 MB Pi that also runs the bot and zigbee2mqtt

Per the PR doc this branch has never run on the Pi. Doing a first run of new code at 16:00 on a box
with a power fault is a bigger bet than repairing what is there.

## Independent of all of it: the power supply

**1006 under-voltage events in 7 days** (`0x00050005`), plus 327 `uvcvideo: Failed to resubmit video
URB` camera errors, and the old sampler died of **SIGBUS** — the signature of a failing mmap'd V4L2
buffer. PIPELINE.md §3 says it outright: *"Fix first, independent of all of the above: the power
supply."* No unit file fixes that. Bring a 5 V 3 A supply and a short cable.
